# Dot → Harness 插件：能力与安装体验审查

审查日期：2026-10-22。基线：`0.4.0-preview.1`，代码提交 `28d26eb`，交付记录 `caf1cb1`。本轮为审查与建议，未修改运行代码、安装包或服务配置，未派发新的模型任务。

## 结论与产品定义

**面向用户，它就是一个 DeepSeek Harness 插件，让 Dot 能读取 Harness 项目、派活、继续、查询结果和叫停。** “连接器”描述连接两端的用途，“插件”描述用户安装和使用它的方式，两者并不矛盾。

现有实现确实包含原生 Harness 插件 `dot-dsh-management`，页面叫「Dot 连接」。完整通路还依赖本地读取/管理服务、Tunnel，以及用户账号中的私有 Dot 工具连接。当前把这些交给操作者分开部署，导致“装了插件为什么还不能用”的困惑。对外应该提供一个明确的 Harness 插件安装入口，把配套组件放到插件管理之下。

核心执行闭环已有实际 Dot 与本机 Host 的关联证据，见 [verification.md](verification.md)。此次增强的重点是普通用户安装、任务接续、异常恢复与持续使用，不需要重新退回只读或公开测试项目。模型、工具与审批继续沿用用户自己的 Harness 配置。

## 核对范围与证据边界

- 读取安装入口、README、runbook、原生插件、MCP 工具、管理器与任务账本的当前源码。
- 通过原生 CUA 检查真实 Harness：总览显示「连接正常」、读取/任务入口在线、已有调用与任务计数。私有原图保存于 `[local private evidence omitted]`，未放入公开文档或安装包。
- 点击任务页时，AX 曾返回 `dot-management/unavailable`；随后窗口被外部工作切换到插件设置页。本轮停止 UI 操作以避免干扰并行安装，不能将后续截图当作任务页截图，也不能据此宣称所有页签验收通过。
- 后台有界复核：任务列表、总览和访问记录单独请求均成功；一次三个管理请求同时发出时出现 `403 MANAGEMENT_DENIED`，另一次全部成功。证实存在与时序相关的并发拒绝通路；缺少当时逐请求日志，不能将该通路断言为原始 UI 错误的唯一原因。
- 首次安装、更新、卸载、重启恢复与审批等待流程本轮未实际执行。相关结论是源码审查，不是完整新设备验收。未做 WCAG 合规审计。

## 用户流程的主要问题

| 用户步骤 | 当前情况 | 优先优化 |
| --- | --- | --- |
| 安装插件 | 有原生插件，但主包入口仍连接旧 fixture；依赖手配多个服务 | 统一一个安装入口，首次自动预检并准备本地组件 |
| 连接自己的 Dot | 需要账号侧私有连接与 Tunnel 配置 | 插件引导本人登录授权，显示当前连接对象及下一步 |
| 确认可以使用 | 「连接正常」只依据部分本地状态 | 分别核对读取、执行 worker、Tunnel 和实际 Dot 回连 |
| 派活和看进度 | start/get/followup/cancel 已有；无 Dot 任务列表 | 能找回任务、显示当前阶段、最近活动和待处理事项 |
| 在 Harness 接手 | 列表显示项目 ID，详情显示会话 ID | 显示项目名和任务名，直接打开对应原生会话 |
| 处理错误 | 通用错误提示；单项失败会清空整个页面 | 保留最后可信状态，指出失败环节和可执行恢复动作 |
| 长期使用 | 累计 100 个 job 硬上限；外部服务无统一生命周期 | 归档、容量提示、受控恢复、更新与卸载管理 |

## 第一优先级：收成普通用户能安装、能持续用的插件

### 1. 一个安装入口，三个用户步骤

目标流程：**安装 Harness 插件 → 连接自己的 Dot → 从 Dot 完成一次小任务。**

插件应自动发现当前 profile、检查版本/运行时、生成自己的私有配置与凭据、启动并管理自己的服务。首次页面只说明用途、访问范围及「连接 Dot」；端口、token 文件、JSON 和进程详情放到诊断页。

账号登录及平台要求的授权仍由本人完成；插件不能替别人获得账号权限，也不能分发作者的私有连接。首次成功应来自实际 Dot 的回连和任务结果。读取到本地服务在线只能算本地准备完成。

当前“一句话安装”是交给 Agent 执行配置的指令，还不是独立的一键安装器。相关证据：`README.md:9–15`、`index.js:1–4`、`src/plugin.js:8–18`、`management-plugin/index.js:77–89`、`docs/operator-runbook.md:23–51`。

发布前验收：新 profile 按单一入口安装；只需本人完成必要账号授权；不用手改 JSON 或终端启动服务；实际 Dot 成功读取、派任务、拿结果、继续和取消。明确支持的 OS/版本；现有读取器含固定 macOS 路径、特定 SDK 检查和外部 Python 依赖，不能宣称跨设备通用。

### 2. 连接状态必须能说明“现在能不能接活”

现有 `harness_status` 只描述读取服务；管理总览用 `Boolean(nativeTasks)` 判断任务入口在线。任务账本存在不能证明 renderer worker 正在工作，更不能证明云端 Dot 已连接。

建议统一能力状态，返回可读/可派活范围、worker 最近心跳、云端连接最近验证时间。区分「本机就绪」「Dot 已连接」「暂停接入」「等待授权」「连接中断」。云端实时状态取不到时明确显示最后验证时间，不假装实时正常。

列表请求失败不应把已成功读取的总览一起清空。当前 `client.js:25–31` 的 `Promise.all` 将两者绑定，一项失败即显示笼统的「连接状态待核实」。恢复动作应匹配实际失败原因，例如重新连接、重试任务列表或查看诊断；不能全部要求用户反复刷新。

本轮还确认一个应优先修复的并发问题：管理器最多接收两个并行管理请求，而后台 worker 周期性请求 overview，任务页同时请求 overview 与 jobs，可能叠成三个。第三个请求会被拒绝，适配器再将其显示为服务不可用。应区分控制流与页面查询，合并/排队读取，保留可诊断的繁忙状态；不能仅靠用户不停刷新。一次有界三并发读取已重现拒绝，但原始 UI 错误的具体归因仍需请求级日志。

依据：`src/harness-reader.js:149`、`src/management.js:81,85`、`management-plugin/src/client.js:25–31,50–51,63–64`、`management-plugin/src/native-worker.js:127,135`、`management-plugin/index.js:69`。

### 3. 任务能够回找，并明确什么需要人处理

Dot 目前只能凭已知 job ID 查询、继续或取消，管理器已有任务列表却没有对应的 Dot 工具。增加最近任务列表，按项目/状态查找，按稳定 request ID 回找；换聊天后仍能找回工作，超时后不必再派一遍。

原生任务详情已有等待审批/回答数量，但没有问题内容、选项和「打开 Harness 会话」。优先让用户看清卡在哪里并直接跳到原生会话；后续再利用官方问答接口，在明确授权的流程中回答。审批仍沿用 Harness 原生设置和交互。

任务列表显示项目名、简短任务名、当前状态、最近活动；ID 进诊断详情。运行中自动更新，保留当前选中任务，不要求刷新后重新寻找。当前界面只有手动刷新，刷新会清掉详情。

依据：`src/mcp.js:24`、`src/native-tasks.js:34–38,117–124,257`、`management-plugin/src/native-worker.js:62`、`management-plugin/src/client.js:25–35,56,74–76`。

### 4. 消除长期使用的硬障碍

`MAX_JOBS=100` 是累计上限，每次 followup 也增加一个 job；达到上限即 `NATIVE_CAPACITY`。UI 写「最近 100 项」会让人误以为自动滚动保留。需要归档、容量显示和明确的保留策略，同时保留 request 去重索引以及状态未确认的任务。

插件应管理自有进程的启动/退出、版本更新和卸载；卸载时明确区分停止连接、撤销账号连接、保留/删除记录。只处理自己的组件，不能重启其他正在工作的 Host 或全局重载无关插件。

依据：`src/native-tasks.js:6,68,131–138`、`management-plugin/src/client.js:67`、`management-plugin/index.js:83–89`。

## 第二优先级：让调度体验更接近用户预期

1. **运行中补充要求。** 当前 followup 仅接受已结束的任务。官方本地 SDK 有 queue/steer 模式，可设计「本轮完成后继续」「立即补充要求」；必须正确关联追加消息与任务，不能直接删除现有冲突检查。
2. **同项目的任务调度。** 当前多个 start 能创建独立会话并修改同一目录。默认让有冲突风险的项目任务排队；用户明确需要并行时，展示并行条件与工作目录，保留现有授权范围。
3. **重启后的恢复工作流。** 保留当前 unknown 和禁止盲目重放写操作的机制；展示任务已提交到哪里、最后确认的阶段，先核对原会话，再给出可用的接续动作。
4. **结果能直接交付。** 在最终正文之外列出产物、修改文件、运行过的验证与结果；点击打开文件或原生会话。事实来自实际记录，不能靠模型补写成功证明。
5. **完成与内容验收分开但不堆术语。** 主界面用「已完成」「需要你处理」等用户语言；返回字段中的 `acceptance:unverified` 留给详细记录。若做「标记已验收」，必须由用户操作，不能随任务结束自动改变。
6. **已有会话的接续。** 当前能读取已有会话，但只能控制本连接创建的会话。以后可单独设计用户选择会话、确认接续与活动冲突检查，不能宣传为已支持任意会话接管。

依据：`src/native-tasks.js:112–115,149–161`，`management-plugin/src/native-worker.js`，本地官方 SDK `packages/api/session-controller/src/types.ts:344` 与 `packages/interaction/user-questions/src/index.ts:151`。SDK 提供原语不等于连接器已经实现完整体验。

## 页面信息结构建议

- **总览：** 第一行说明能否接活；随后是正在执行、需要处理、最近完成。当前累计调用数移到记录/诊断，减少首屏挤占。
- **任务：** 主工作入口；项目名、任务名、状态、最近活动，支持筛选/搜索、打开原生会话、查看产物、继续及取消。
- **访问记录：** 次级记录入口；用「读取了哪个项目/文件」「派发了什么任务」表达，原始工具名和 ID 收入详情。
- **连接设置：** 首次引导、连接对象、访问范围、暂停新请求、断开、诊断。明确暂停后的已运行任务如何处理，取消任务使用独立动作。
- **首次空态：** 放一句可复制给 Dot 的示例和「检查连接」，让用户知道下一步做什么。

建议先完成安装整合、状态可信、任务回找与接手、容量归档，再做运行中补充、项目队列和产物交付。完整连接能力与管理界面可用性应分别验收。
