# 在 Dot 回答追问、确认一次操作

Dot 给 Harness 派任务后，可以把该任务的追问和操作请求带回对话。你直接回答问题，或明确选择“本次允许／拒绝”，Harness 继续处理同一个任务。无需自己寻找或复制会话、问题、工具调用编号。

preview.25 已公开发布并通过官方 npm 安装验收。本轮真实 Dot 派发并读取了 Harness 的问题；答复通过正式安装的本机 MCP 提交，原任务已完成。旧 Dot 连接仍缓存 12 个工具，两个新工具在云端的发现和调用尚待刷新验收。各层结果见 [verification.md](verification.md)。

## 使用过程

1. 在 Dot 说明要 Harness 完成的任务。
2. Dot 查询到 Harness 的追问时，展示原问题与选项；你回复选择或自己的答案。操作审批会展示本次请求的工具与原因，需要你明确允许一次或拒绝。
3. Dot 把你的具体答复交回 Harness，继续跟进原任务并返回结果。原会话仍可在 Harness 打开。

正常问题可按原始选项单选、多选或补充文字。涉及操作批准的问题只接受本次具体选择，不提供“今后始终允许”。笼统的“把任务做完”不等于逐次批准。

普通阻塞问题在原执行轮次中继续；原生计时问题超时后仍可保持待回答，晚到的答案使用 Harness 官方续接机制。系统不会为了等待答复更改原来的超时设置。

## 连接与状态

Dot 连接需能发现 `harness_answer_question` 和 `harness_decide_approval` 两个新工具。若旧连接仍缓存先前的工具集合，先完成连接能力刷新；仅升级本机包不会证明云端已发现新工具。

本版仍由 Dot 查询任务状态来取得问题和结果；尚不把它描述成用户离线时可主动推送通知。桌面上的手动接管、已处理的请求、替换的卡片或取消会使旧远程答复失效。

提交答复得到“已受理”后，还需核实 Harness 已记录这次处理。结果不明确时保留待核实，不重复批准；明确尚未提交的失败可以在重新查询同一请求后修正重试。

## 工具约定

先用 `harness_get_task` 读取当前 `interactions`。Dot 隐藏技术编号，并在工具调用中传回原编号：

- `harness_answer_question`：`job_id`、`interaction_id`、幂等 `request_id`，以及 `answers:[{id,selected:[选项原文],custom?:补充文字}]`。
- `harness_decide_approval`：相同身份字段与 `decision:allow_once|deny`。只处理一个准确请求，不改变会话级长期权限。
- `harness_get_task`：返回这次答复的 `interaction_operations` 回执，以及原任务的后续状态。

回答通过原生结构化通道提交，不会作为新的普通任务提示词。相同 `request_id` 与相同内容复用原回执；相同 ID 换内容会冲突。问答／审批控制不会排在正等待它的任务后面。

服务器验证请求与任务、会话、消息及执行轮次的关联。用户逐次确认由 Dot 与其客户端界面承接；服务器不把模型填写的布尔值当作真人点击证明。暂停接入时不接收会恢复执行的回答或允许；拒绝原生操作审批仍可用。其他仍可在 Harness 处理的请求会保留原入口。

## 本机数据

为了任务恢复、去重和核对提交结果，本机私有任务状态会保存题面、选项、审批原因及你的结构化答复，并随有界命令历史保留；原生 Harness 会话也保留答复。访问审计仅记录请求标识、操作类型与结果，不记录答复正文。本版没有新增第三方消息转发服务。
